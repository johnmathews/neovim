# vim.NIL on 0.12: Verified, Harmless Here

**Date:** 2026-10-11

## Question

Neovim 0.12's news says JSON null now reaches Lua as `vim.NIL` (F29). A plugin that tests an LSP field for truthiness
would read `vim.NIL` as true. If navic or aerial did, breadcrumbs or the outline would degrade silently after the
upgrade. W19 is a verification unit: its deliverable is the observation.

## Method

The same probe on both versions, with the LSP log at TRACE: 0.11.6 against main@8728d88 (a `git archive` snapshot in the
scratchpad) and 0.12.6 against the Stage B branch, on the Python, Lua, TypeScript and YAML samples. Per buffer it asked
navic for its location inside a symbol, loaded aerial on its LSP backend, converted the document symbols the way
Telescope's `lsp_document_symbols` does, requested completions and resolved the first three, and finally read `:messages`
and the logs. The evaluation had only read `news.txt`; this exercises the plugins against real server responses.

Two probe mistakes came first. main disables aerial below 0.12, and the first probe required it inside a wait loop, so
the 0.11.6 run hung. And headless Neovim never fires `CursorHold`, which is when navic refreshes, so the first 0.12.6 run
reported empty breadcrumbs everywhere; the probe now refreshes navic's context itself.

## Result

The claim holds. In the 0.12.6 log, 28 received messages carry `vim.NIL`: null `params` on the four `workspace/*/refresh`
requests, null `shutdown` results, `documentSelector` in an `initialize` response, and a field of a documentSymbol
response. The 0.11.6 log has none.

The impact does not. Breadcrumbs, symbol conversions and completions are identical on both versions, aerial outlines
every sample on 0.12.6, nothing errors, and `:messages` stays empty. F29 is regraded: claim [VERIFIED], impact refuted
[VERIFIED]. Nothing to fix. Closes #9.
